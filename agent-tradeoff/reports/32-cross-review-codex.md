# Cross-review of the two UX proposals

Compared `32-ux-review-controller.md` with `32-ux-review-codex.md`, `CONTINUE.md` section 3 and current source on `build/village`. This is a source review, not a fresh live/device test. No code changes.

## What the controller gets right, better than mine

- Its one-line loop and single primary “Start a rumour” explain the activity faster than my longer welcome and competing exploration button. Adopt the primary action; keep dismissal and free exploration available without another prominent choice.
- Three visible story cards and a short listener list make the first decision concrete. My nearby-listener-first route is cheaper to build, but should expose those choices immediately on arrival rather than defaulting to a blank writing task.
- “Menu” is clearer than my “More”; its Play / Settings / For the curious grouping is easier to scan than my five groups. Adopt the simpler grouping, retaining all existing destinations and watching settings.
- Three latest moments with full history under “More detail” sets a useful density limit that my events-first proposal lacked. Adopt that limit, but show the actual reply before the face chain.

## Tracker: possible data, unjustified binary promise

- “Heard by 3 · believe it 2 · doubt it 1” is not an existing simulation statistic. Unique hearing and continuous confidence are computable; the proposed exhaustive believe/doubt split is a new presentation policy, not a stored fact.
- For hearing, filter `trailHistory.links` by the selected claim and count unique `to` IDs. `ui/app.ts:consumeEvents()` records `snapshot().threads` through `ui/rumor-trail.ts:createTrailHistory()`. `sim/agents/hearing.ts:afterHear()` supplies actual non-self transmissions, including the initial whisper via `hearFromStranger()`. Snapshot threads alone are bounded in `sim/engine.ts`; counting their current length loses history and repeats listeners.
- Start at the first matching transmission from `stranger` in recorded order if labelling it the player's journey; a tick cutoff alone can include earlier same-tick tellings. Existing authored claims can circulate beforehand; even later matching tellings do not establish that the player caused them. Do not count witnesses who merely saw a whisper, self-observation, corrections or every `belief` event as hearing. The internal `strangerClaims[].heardBy` set is not exposed by `Simulation` and is not a ready UI field.
- For current belief, iterate `sim.cast` IDs and read `sim.inspect(id).beliefs.find(b => b.claimId === selected)?.confidence`. The public types are in `sim/types.ts`; `sim/engine.ts:inspect()` delegates to `sim/agents/inspect.ts:inspectAgent()`, which reads `packages/rumormind/src/belief.ts:BeliefLedger.confidence()`. `WorldSnapshot` has no belief totals. Missing belief is unknown, not disbelief; historical `belief.after` values can miss subsequent fading.
- If shipped later, classify only the counted hearers, document thresholds and include “Unsure”; e.g. above 0.6 / below 0.4 / otherwise unsure is a proposed UI convention. `ui/debrief.ts` uses above 0.6 for a specific challenge, not a universal binary classifier. A spoken `line` with `act === 'doubt'` records expressed doubt, which differs from current confidence. Never derive agreement from faces, transmission links or reaction wording.
- For two days, ship an honestly scoped “Heard by N people since your whisper” and recorded replies; defer belief totals. Recompute on simulation ticks and rebuild/reset on rewind, without simulation writes or per-frame inspections. The example numbers must never be scripted as a promised outcome.

## Walking, following and naming

- Automatic walking after an explicit listener choice is good and already supported by `ui/app.ts:walkToVillager(id, true)` and `followStep()`. It need not change simulation rules. Use awake, reachable choices, exclude the selected claim's subject (`sim/agents/stranger.ts:whisper()` rejects them), show the destination and cancellation, and handle a listener moving or sleeping before arrival. No teleport, forced whisper or guaranteed travel time.
- The controller's story-first wizard is more work than “only what is shown first”: `ui/whisper.ts:build()` clears `ownText`, `selected` and confirmation whenever reopened. Keeping a story through walking needs explicit draft state and renewed preview when relevant details change. For this build use the existing listener/walk-first route; defer the reversed wizard rather than lose text or silently send it.
- The “following is off” diagnosis is incomplete: `ui/app.ts:doWhisper()` already calls `showTrail(true)`, which enables threads and `focus.toggle(true)`; the render loop follows new transmissions. `watchBeats` starts false and separately controls readable exchange playback. Verify deployed state/styling before prescribing another default-on call.
- My separate post-send “Watch” choice adds friction too. Retain the existing camera-follow default after an explicit whisper, explain it before sending, expose Stop/Resume, respect an explicit off choice on later whispers, and preserve manual-camera takeover and reduced motion. Keep slower conversation playback separately opt-in. Forced camera recapture on every telling would be a UX regression, not a determinism or typed-consent rule breach.
- Final labels: **Map / Rumors / Menu**. Map is a clear shared improvement. Controller's “Your rumour” is too narrow for multiple player claims and the retained all-village view; use “Your latest rumor” inside Rumors. Menu beats my More. Keep one spelling consistently across controls, headings and help; renaming alone is not a rule violation.

## Rules and scope the proposal misses

- Copy: its tracker uses forbidden middle dots. Use separate sentences/rows, sentence case, plain words, no all-caps labels, button arrows or exclamation marks. Its main loop should say “See what people think”; belief is not truth, spread is not guaranteed, and lack of a mandatory goal is not a defect. Keep the challenge optional.
- Phone/postbox: a 390 px walkthrough does not satisfy 360 px. More bottom controls and a persistent tracker need reserved space, wrapping, keyboard-aware action visibility and focus handling. `styles/app.css` currently gives the phone `.story` `bottom: 0`; both compact and expanded views need explicit postbox clearance. Neither proposal's layout prose proves compliance.
- Typed consent: “Write my own” must retain `ui/whisper.ts:prepare()`'s exact-wording preview, meaning/reputation information and disclosure of dialogue, research exports and shared replay links, followed by a separate explicit send. Editing text/listener invalidates confirmation; neutral fallback still needs confirmation. No automatic send after walking, server logs/shared caches of drafts, or prose in share-card images. A sample card should display the actual existing claim text, not a shortened label that sends different words.
- Determinism: read-only counts, UI walking commands and camera defaults can preserve the model and replay pin. Do not fabricate gossip, add wall-clock/random simulation decisions, change belief thresholds in the model, add dependencies or loosen API caps. Any actual simulation change requires replay inspection and the prescribed pin process. A compact Time control must retain speeds, scrub/replay and stepping; “all features stay” needs that explicit inventory.
- My own review also needs correction: current `ui/whisper.ts` already uses a boat-story placeholder, so both death-placeholder findings describe the supplied/live screenshots, not current source. Verify deployment rather than repeat an obsolete source fix. My proposed scope was too broad for two days; defer the wizard and belief dashboard.
